# Meta Product Feed — "File format isn't supported" — Debugging Log

**Status:** UNRESOLVED. Parked here until we sit with Meta / the CMO together.

## TL;DR

Meta Commerce Manager rejects our feed URL with:
> "Your file format isn't supported. Make sure the file is in XLSX, CSV, TSV, RSS XML or ATOM XML format"

The file itself is byte-perfect, valid RSS/XML, served uncompressed, directly (no redirect) —
verified multiple times, including the CMO testing the raw URL directly. Meta still rejects it.
We've run out of things we can fix blind on our side. Next step needs either info from Meta's

## Current feed URLs

- Public-facing (registered with Meta): `https://www.mega-events.co.il/feeds/meta-catalog.xml`
  — 307-redirects to the storage URL below.
- Actual file (raw, direct): `https://fandqafngybfdyslofmr.supabase.co/storage/v1/object/public/public_resources/feeds/meta-catalog-feed.xml`
- Generated by: `myt-main` app renders the feed → `myt-backoffice` cron
  (`app/api/cron/publishMetaFeed/route.ts`, every 15 min, `vercel.json`) fetches it with
  `Accept-Encoding: identity` and republishes the raw bytes to Supabase Storage.

## Why it's built this way (root causes already found + fixed)

1. **Vercel edge force-compresses every response with Brotli** whenever the client's
   `Accept-Encoding` includes `br` — confirmed live, and NOT overridable from app code via:
   origin `Content-Encoding: gzip`, `Cache-Control: no-transform`, switching `force-dynamic` →
   ISR/`revalidate`, or `Content-Type: application/octet-stream`. All four tested live, all
   ineffective. This is a platform-level behavior, not something our route code controls.
2. Working theory: Meta's fetcher advertises `br` support in `Accept-Encoding` but doesn't
   actually decode it, so it receives undecodable binary and rejects the feed as
   "file format isn't supported." (Not confirmed by Meta — see Open Questions.)
3. Workaround: republish the feed as a static file in **Supabase Storage** (different CDN,
   no Vercel edge in the path), and have the public route just 307-redirect there.
4. **Supabase Storage is ALSO Cloudflare-fronted and ALSO force-Brotlis** any response whose
   `Content-Type` looks like compressible text (confirmed live — `application/rss+xml` and
   `application/xml` both get `content-encoding: br` from Cloudflare for a client advertising
   `br`). The only way found to make Cloudflare skip compression: upload with
   `Content-Type: application/octet-stream`. Confirmed live: no `content-encoding` header,
   `content-length` matches the original file exactly.
5. Cloudflare **also cache-poisons** on re-upload with the same content but a different
   `Content-Type` — it validates purely on the content-hash etag and keeps serving a stale
   cached response (headers included), never re-fetching from origin. Fixed by moving to a
   never-before-cached storage path (`feeds/meta-catalog-feed.xml`, not the original
   `feeds/meta-catalog.xml`).

Net result: the file that's live right now is 100% byte-identical to what our app generates,
served with **no compression at all**, and reachable with a stable, non-redirecting URL if you
hit the storage URL directly.

## What's been tested and ruled out

| Hypothesis | Test | Result |
|---|---|---|
| Vercel forces `br`, corrupts response | curl with/without `Accept-Encoding: br` against the Vercel route | Confirmed — `br` forced regardless of our headers |
| `Cache-Control: no-transform` stops it | Set on Vercel route | No effect, still `br` |
| ISR/static instead of dynamic stops it | Switched route to `revalidate = 900` | No effect, still `br` even on `PRERENDER` cache hits |
| `Content-Type: octet-stream` stops Vercel's compression | Tested directly on the Vercel route | No effect (this trick only works on Cloudflare, not Vercel) |
| Meta doesn't follow the 307 redirect | **CMO tested the raw storage URL directly, bypassing our redirect entirely** | **Still the same error** — this hypothesis is FALSIFIED |
| File bytes are corrupted/truncated | curl body dump of the live storage URL | First bytes are a clean, valid `<?xml ...><rss ...><channel>...` — 287,420 bytes, matches source |
| `Content-Type: application/octet-stream` itself gets rejected by Meta (generic type) | Re-uploaded a test copy with `Content-Type: application/rss+xml` | Cloudflare immediately force-Brotli'd it (`content-encoding: br`) — so this variant reintroduces the original suspected problem. Never actually tested against Meta (didn't want to burn another registration cycle without a clearer signal) |

Dead end via this API. |

## Read Meta's own spec (the link Dor sent)

`https://www.facebook.com/business/help/120325381656392?id=725943027795860` —
"Product Data Specifications for Catalogs in Commerce Manager." Relevant section,
**"Data file formats and specifications"**:

- Supported formats: CSV, TSV, Excel (XLSX), Google Sheets, or XML (RSS/ATOM).
- "Your file must begin with a valid `<?xml` declaration tag." — **ours does**, verified.
- "Your URL must begin with `http://`, `https://`, `ftp://` or `sftp://` and must link to your
  file, not to your website or somewhere else." — arguably rules out redirects, but the CMO's
  test bypassed our redirect entirely and still failed, so this isn't it either.
- **Nothing in the spec mentions Content-Type headers or response compression at all.**

Per Meta's own documented rules, our file should be accepted. It isn't. The gap is in
undocumented behavior on Meta's fetching/validation side, or in infrastructure we don't
control (see below).

## Leading unconfirmed suspect: Cloudflare Bot Management

Every response from the Supabase Storage domain includes a `__cf_bm` cookie — this is
Cloudflare's **Bot Management** cookie, confirming it's active on that CDN zone (which we do
not control; it's Supabase's shared infrastructure). It's plausible Meta's crawler gets
challenged/blocked at Cloudflare's edge (served an HTML interstitial instead of the real file)
even though our own curl requests get the real bytes — bot scoring can differ by requester
IP/ASN/fingerprint. This would produce exactly this symptom (generic "format not supported")
and would be completely invisible to us since we can't spoof Meta's crawler identity to test it.
