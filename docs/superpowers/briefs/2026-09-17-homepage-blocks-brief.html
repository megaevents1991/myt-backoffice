3. Ask Dor the open questions from the brief ONE BATCH at a time (he answers in Hebrew, short). Offer options with a recommendation - he likes to choose, not be told.

5. Stop after the spec and ask for approval. Only after approval: superpowers:writing-plans for the implementation plan.

Hard rules: schema lives in this repo only (supabase/migrations, master only, merge master first, idempotent SQL); main app never runs migrations; section keys are mirrored in both repos; update app/(dashboard)/guide/guide-content.ts in the same PR as any flow change; never commit or push unless Dor asks.

  • עמודי /c/ והאבים אנכיים (VerticalHubPage) - האם הם מועמדים לאותה תשתית.

אילוצים שהאפיון חייב לכבד

  • הסכמה בבעלות ה-backoffice. מיגרציות רק ב-supabase/migrations/, מוחלות אוטומטית במיזוג ל-master, אף פעם לא מ-branch. git fetch && merge origin/master לפני npm run db:new. SQL אידמפוטנטי.
  • main לא נשבר בגלל הלוח. כל כשל בקריאה = לייאאוט ברירת מחדל. בלוק מסוג שהקוד של main עוד לא מכיר חייב להתעלם ממנו בשקט (סדר פריסה: main קודם, אחר כך backoffice - או להפך, האפיון מחליט ומנמק).
  • מפתחות משוכפלים בשני הריפואים. מעבר לסקשנים דינמיים מבטל את ה-as const - צריך תוכנית מעבר שלא שוברת את 7 הקיימים ואת ה-pins שכבר נשמרו.
  • כתיבות מפורשות. אין spread של אובייקט מהקליינט ל-insert/update; ולידציה בצד שרת לכל שדה של בלוק.
  • shadcn/ui בלבד בלוח, בלי ספריות UI חדשות; גרירה היא HTML5 מקורי היום.
  • ביצועים בדף הבית. כרטיסי הקרוסלה נטענים lazy בכוונה (לחץ זיכרון תמונות ב-iOS). גלריה/באנרים לא יכולים להחזיר את הבעיה.
  • המדריך. כל שינוי זרימה מעדכן את guide-content.ts באותו PR, אנגלית + עברית.
לא לגעת: שרשרת המחיר, events, וחוקיות המילוי האוטומטי של most_wanted / newest - הן מחוץ להיקף. הבלוקים החדשים הם תוספת לצדם.
