## 1. שירות מחירים אחד — `lib/services/price-quote.ts`

מודול אחד שכל צרכני המחיר עוברים דרכו: כפתורי הטופס, מילוי אוטומטי ביצירה (סעיף 4),
ה־cron (סעיף 3), מצב אמן (סעיף 6), המפעל (סעיף 8). מספר אחד בכל מקום.

### `quoteFlight(cityIata, departDate, returnDate)`

1. שתי קריאות `POST /api/flights/search` (ה־route הקיים, כבר מקבל `nonStop`):
   - `nonStop: true` → הטיסה הישירה הזולה (`direct`)
   - `nonStop: false` → הזולה בכלל (`any`, בפועל הקונקשיין הזול או הישירה עצמה)
2. בחירה: אם אין `direct` → `any`. אם `direct − any > 300` → `any`. אחרת `direct`.
3. `base_flight_price = round10(chosen + 100)` — המרג'ין לפני העיגול.
4. שתי הקריאות נכשלו / אין הצעות → `null` (הקורא מחליט: שדה ריק + אזהרה, אף פעם לא 0).

### `quoteHotel(lat, lon, checkin, checkout)`

1. `GET /api/hotels/search` הקיים (פרוקסי ל־main; main כבר מחזיר 3★ הזול —
   `total_4star_hotels_found` הוא שם legacy שקרי, אין שינוי ב־main).
2. `base_hotel_price = round10(cheapest + 120)`.
3. כשל → `null`.

### קבועים (באותו קובץ, מיוצאים)

```ts
FLIGHT_MARGIN_USD = 100
HOTEL_MARGIN_USD  = 120
DIRECT_GAP_USD    = 300   // מעל זה עוברים לקונקשיין
SYNC_DEVIATION_USD = 150  // סף עדכון ב-cron
SYNC_FREEZE_USD    = 400  // מעל זה - "דורש בדיקה"
```

**שינוי התנהגות קיים:** כפתורי "Search Flights" / "Search Hotels" בטופס האירוע ממלאים היום
את הזול ביותר בלי מרג'ין. הם עוברים ל־price-quote — כלומר מהרגע הזה כפתור ידני מחזיר
מחיר עם +100/+120 ועיגול לעשרות. זו ההתנהגות הרצויה (המספר של הכפתור = המספר של ה־cron).

## 2. ניקוי טופס האירוע (שלב ו — S)

- שדות markup שאינם `ticket_only_markup` / `event_additional_markup` נכנסים לסקשן
  "מתקדם" מכווץ (Collapsible). אירוע שנטען עם ערך ≠ 0/ברירת מחדל באחד מהם — הסקשן
  נפתח אוטומטית. הרשימה המדויקת נקבעת מהטופס בזמן מימוש (בערך חמישה שדות).
- `usual_price` יורד מהטופס לחלוטין. **העמודה לא נמחקת:** main משתמש בה כ־fallback
  אחרון בפיד (אירוע sold-out בלי מחיר מחושב — `feedPriceUSD`), ואירועים ישנים מחזיקים
  ערכים. אירוע חדש יישמר עם 0 כמו היום כשלא מולא.
- תמונת קארד אוטומטית: אם `card_image_url` ריק בעת שמירה ויש קריאייטיב בגלריה של
  האירוע — נלקח ממנה. ידני תמיד גובר.
- auto-tags ביצירה: קריאה ל־auto-tagger הקיים (taxonomy v2) על אירוע חדש.

## 3. cron סנכרון מחירים (שלב ג — L)

**קבצים:** `app/api/cron/base-price-sync/route.ts` + `lib/services/base-price-sync.ts` +
מיגרציה `base_price_sync_log` + entry ב־`vercel.json` + מסך דשבורד + מייל.

### אלגוריתם (פר אירוע, פר רכיב טיסה/מלון בנפרד)

```
live  = price-quote (אותו שירות, אותם מרג'ינים)
delta = |live − base|
delta < 150            → כלום
150 ≤ delta ≤ 400      → base = live (כבר מעוגל), רישום בלוג status='applied'
delta > 400            → אין כתיבה; רישום בלוג status='needs_review'
```

דו־כיווני — מוריד base גבוה מדי ומעלה נמוך מדי.

### מי בפנים / בחוץ

- בפנים: אירועים חיים (`is_deleted IS NULL`), עתידיים, עד יומיים לפני האירוע.
- בחוץ: רכיב עם offline מקושר (טיסת offline → אין סנכרון טיסה; מלון offline → אין
  סנכרון מלון), רכיב עם base = 0 (אין רכיב), ticket-only.
- קצב: `date` בתוך 45 יום → כל לילה; רחוק יותר → פעם בשבוע
  (`event.id % 7 === new Date().getUTCDay()` — `Event.id` הוא number).
- תקציב זמן כמו `nightlyTixstockPriceSync`: עצירה לפני timeout, דיווח `remaining`,
  המשך בלילה הבא. `maxDuration` בהתאם.

### `base_price_sync_log` (מיגרציה, backoffice בלבד)

```sql
id bigint identity PK, event_id, component text ('flight'|'hotel'),
old_price int, new_price int, live_price int,
status text ('applied'|'needs_review'|'error'), note text, created_at timestamptz
-- RLS on, בלי policies (service-role בלבד) - כמו tasks
```

### dry-run — חובה

`?dry_run=1` (וגם בריצה ידנית עם ה־`?key=` legacy): מחשב הכול, מחזיר JSON של מה היה
משתנה, **אפס כתיבה ל־events ואפס רישום ללוג**. ככה בודקים על ה־preview — שמדבר עם
פרוד DB — בלי לגעת בכלום.

### שקיפות

- מסך "שינויי מחיר" (route בדשבורד): טבלת הלוג + פילטר needs_review + כפתור
  "אשר עדכון" לשורות שנעצרו (מחיל את live ומסמן applied).
- מייל יומי דרך `lib/email.ts`: "עודכנו X · ממתינים לבדיקה Y · שגיאות Z" + קישור למסך.
  נשלח רק אם X+Y+Z > 0.

## 4. זיכרון אצטדיון + מילוי אוטומטי ביצירה (שלבים א+ב — M+M)

**זיכרון אצטדיון** (בתוך זרימת היצירה, `tixstock-to-event.ts` והגנרליזציה שלו):

- איתור האירוע האחרון באותו venue: התאמת שם אצטדיון (normalized), גיבוי — קרבת
  קואורדינטות (< 1 ק"מ). מהאירוע שנמצא מועתק **מבנה** `tickets_and_rates` בלבד:
  שמות, תיאורים, צבעים, אזורים — בלי מחירים.
- מחירים: מנגנון ה־reprice הקיים בוויזרד מול listings חיים. קטגוריה בלי listing
  תואם → המחיר הישן + דגל "לבדיקה" (ברמת ה־UI, לא בסכמה).
- בבאץ': מוחל אוטומטית בכל שלב + הודעת "הועתק מ־[שם האירוע]" + כפתור ביטול.
- בלי טבלה חדשה — הזיכרון הוא האירועים הקיימים.

**מילוי base ביצירה:** ברגע שיש `city_iata` + תאריכי טיסה — `quoteFlight` +
`quoteHotel` רצים ברקע וממלאים **רק שדות ריקים (0)**. מילוי עם הדגשה עדינה; כשל →
נשאר ריק + אזהרה קטנה, לא חוסם שמירה.

## 5. רב־קבוצות + מצב תחרות (שלב ד — M)

- מסירים את האיפוס בהחלפת מבצע (`tixstock-events-content.tsx`, ~שורה 321): הבחירה
  מצטברת, שורת צ'יפים "קבוצה × n משחקים", ניקוי פר קבוצה.
- הוויזרד (`/events/new?batch=1`) מקבל את הרשימה ממוינת קבוצה → תאריך; הטופס הנגרר
  מתאפס במעבר קבוצה (וזיכרון האצטדיון נכנס מחדש).
- מצב תחרות: בחירת `category_name` (למשל Champions League) → רשימת הקבוצות
  המשתתפות → סימון קבוצות → משחקי הבית שלהן נבחרים אוטומטית (החלטה 4: שם האירוע
  מתחיל בשם הקבוצה; אחרת מסומן לבחירה ידנית).

## 6. מצב אמן — סיבוב הופעות (שלב ה — S–M)

- כל שלב בוויזרד: `city_iata` אוטומטי — קואורדינטות ה־venue מול `locations`
  (≤ 50 ק"מ). אין התאמה → נשאר ידני.
- price-quote פר עיר (סעיף 4 עושה את זה ממילא ברגע שיש iata).
- זיכרון venue (סעיף 4) פועל אם ה־venue מוכר; נכסי האמן (תמונות, תיאור, tags)
  ממשיכים להיגרר בין השלבים כמו היום.

## 7. batch wizard לכל ספק (חדש — M–L)

הזרימה הקיימת: מולטי־בחירה בטבלת הספק → stash `localStorage` → `/events/new?batch=1`.
מוכלל:

- mapping פר ספק: `live-to-event.ts`, `p1-to-event.ts`, `sports-to-event.ts` — לצד
  `tixstock-to-event.ts`, כל אחד נגזר מלוגיקת "צור אירוע" הבודדת שכבר קיימת ב־
  `[id]/page.tsx` של אותו ספק (חילוץ, לא כתיבה מחדש).
- מולטי־בחירה + כפתור "Batch create" בכל ארבע טבלאות הספקים.
- stash אחיד: `{ provider, rows }`; הוויזרד בוחר mapping לפי `provider`.
- סעיפים 4–6 (זיכרון, מחירים, iata) עובדים לכולם כי הם על שכבת האירוע.

## 8. המפעל (שלב אחרון — XL)

**מיגרציה `event_drafts`:** טבלה נפרדת — main לא קורא אותה, אפס סיכון דליפת טיוטה.

```sql
id uuid PK, source text, scope jsonb,       -- מה ביקשו: קבוצה/תחרות/אמן/ספק
payload jsonb NOT NULL,                     -- אירוע מלא, המבנה ש-createEvent מקבל
status text default 'building',             -- building|ready|needs_input|approved|created|error
missing jsonb default '[]',                 -- מה לא התמלא: ['city_iata','base_hotel_price',...]
error text, created_by uuid, created_at, updated_at
-- RLS on, בלי policies
```

**זרימה:** מסך `/factory` → בחירת היקף (קבוצה / תחרות / אמן / ספק+סינון) → בנייה
ברקע: כל טיוטה עוברת את אותן אבנים (mapping ספק → תאריכים חכמים → iata → זיכרון
אצטדיון → price-quote → תמונה → tags), כל שדה שלא התמלא נרשם ב־`missing` →
**גריד סקירה:** שורה = טיוטה; עמודות = השדות האנושיים (iata, מחירים, תמונה, שם);
עריכה inline; שורות `needs_input` מודגשות; בחירה מרובה → "אשר" → `createEvent`
מה־payload פר שורה, status=created (או error + הודעה). טיוטות שנוצרו/נזנחו נמחקות
פיזית אחרי 30 יום (טבלת עבודה, לא היסטוריה — הלוג האמיתי הוא האירוע שנוצר).

**בנייה ברקע בפועל:** צעד־צעד מתוך הדפדפן (loop על server action, כמו סנכרונים
ידניים קיימים) — לא cron. היקף גדול נתקע → משדרגים ל־route עם `maxDuration`.

## 9. בדיקות פר שלב (על הברנץ')

| שלב | איך בודקים |
|-----|-----------|
| price-quote | כפתורי הטופס על אירוע אמיתי בפריוויו — +100/+120, עיגול, כלל ה־300 |
| ניקוי טופס | אירוע ישן (מתקדם נפתח לבד) + חדש (מכווץ, בלי usual_price) |
| cron | `GET …/api/cron/base-price-sync?key=…&dry_run=1` על הפריוויו → דוח JSON, אפס כתיבה. הפעלה אמיתית רק אחרי merge |
| זיכרון+מילוי | יצירת אירוע באצטדיון מוכר → קטגוריות מועתקות, מחירים מתמלאים ברקע |
| רב־קבוצות | בחירת 2 קבוצות → צ'יפים → וויזרד מקובץ; מצב תחרות על Champions |
| אמן | סיבוב הופעות — iata מתמלא פר עיר |
| ספקים | Batch מכל טבלת ספק → וויזרד עם ה־mapping הנכון |
| מפעל | scope קטן (קבוצה אחת) → גריד → אישור 2 → אירועים באתר |

מיגרציות (`base_price_sync_log`, `event_drafts`): כמו תמיד — קובץ המיגרציה לבד
מגיע ל־master (cherry-pick), ה־workflow מחיל, חוזרים לברנץ'. שתיהן additive.

## 10. סדר עבודה וקומיטים

1. price-quote + חיבור כפתורי הטופס
2. ניקוי טופס (ו)
3. cron + מיגרציית לוג + מסך + מייל (ג)
4. זיכרון אצטדיון + מילוי ביצירה (א+ב)
5. רב־קבוצות + תחרות (ד)
6. מצב אמן (ה)
7. batch לכל ספק
8. מפעל: מיגרציה + בנייה + גריד

כל שלב: קומיט(ים) משלו, `tsc` + lint נקיים, push לפריוויו כשדור אומר. QA של דור
אחרי כל שלב עיקרי — לא הכול בסוף.

## חוצה־פרויקטים

- **אין שינוי ב־main.** ה־hotels API כבר 3★; `usual_price` נשאר בסכמה; `event_drafts`
  ו־`base_price_sync_log` הן טבלאות backoffice שאין ל־main סיבה לקרוא.
- שינויי מחירים של ה־cron משנים מה שלקוחות רואים — בכוונה (זו המטרה). בלם ה־$400 +
  dry-run + מסך הלוג הם ההגנות.

## מחוץ להיקף

- AI agent (החלטה 11), עמודת draft על `events`, שינוי כלל "עשרות מינוס 1" לכרטיסים,
  מחיקת עמודת `usual_price`, שינויי UI ב־main.
