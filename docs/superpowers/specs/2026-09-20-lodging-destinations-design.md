## 1. חלק A - אירוע כרטיס-בלבד (סגור מוצרית)

**בקאופיס:** מתג "כרטיס בלבד (ללא טיסה ומלון)" בעורך. דלוק → `ticket_only_markup` חובה; מחירי בסיס / IATA / תאריכי טיסה לא נדרשים; האירוע יוצא מ-`base-price-sync`, `price-light-ours`, alternatives; רמזור חבילה = `na`, רמזור כרטיס כרגיל; פילטר "Ticket only" בטבלה קורא את הדגל האמיתי; אשף הפורטל נעול על כרטיסים.

**אתר:** כרטיס אירוע עם אייקון כרטיס בלבד + תגית "כרטיס בלבד" (בלי טקסט הסבר); "מחיר ממוצע לנוסע" → "מחיר לכרטיס"; מופיע בסליידרים, בחיפוש ובקטגוריות כרגיל; דף הזמנה = כרטיסים → פרטים ותשלום; מחיר = כרטיס + `ticket_only_markup` (בלי 175); פידים: "כרטיס ל…"; `confirm-order` דוחה טיסה/מלון לא ריקים.

## 2. חלק C - שתי ערי לינה

### 2.1 מינוח - תיקון חשוב
במסמך המקורי: MAIN / SUB. בדוגמה של מנצ'סטר/ליברפול זה מתבלבל: במשחק של ליברפול "עיר האירוע" היא ליברפול והטיסה למנצ'סטר; במשחק של יונייטד עיר האירוע *וגם* הטיסה הן מנצ'סטר, וליברפול היא רק תוספת. לכן המודל מדבר על:

- **עיר האירוע** = המיקום הקיים של האירוע (האצטדיון / האולם). כמו היום, הוא גם נושא את קוד ה-IATA של הטיסה.
- **עיר נוספת** = מיקום שני, אופציונלי (שם + נקודה).
- **ליל האירוע תמיד בעיר האירוע** (תשובה 7) - בכל משחק, בלי קשר לאיזו עיר טסים.

### 2.2 מצבי לינה באירוע (בקאופיס)
| מצב | שלב המלון באתר |
|---|---|
| עיר האירוע בלבד (ברירת מחדל - כמו היום) | רשימת מלונות אחת |
| עיר נוספת בלבד (תשובה 5) | רשימת מלונות אחת, בעיר הנוספת |
| הלקוח בוחר - נפתח על עיר האירוע | רצועת לילות, הכול בעיר האירוע |
| הלקוח בוחר - נפתח על העיר הנוספת | רצועת לילות, הכול בעיר הנוספת (חוץ מליל האירוע אם נעול) |
| מסלול מפוצל מומלץ | רצועת לילות עם חלוקה שהבקאופיס הגדיר |

+ **הערת מעבר** (טקסט חופשי): "רכבת מנצ'סטר-ליברפול כ-50 דק'. ההעברה אינה כלולה במחיר." **העברות לא נמכרות** (הוחלט).

### 2.3 רצועת הלילות - הרעיון ל"גמישות מלאה שקלה לכל אדם"
- כל לילה בטיול = כפתור אחד עם תאריך ושם העיר. **לחיצה מחליפה עיר.** ליל האירוע מסומן בכרטיס ונעול.
- מעל הרצועה 2-3 כפתורי קיצור: "המסלול המומלץ" / "הכול ב{עיר האירוע}" / "הכול ב{עיר נוספת}".
- "+ לילה" בשני הקצוות מאריך את הטיול (= שינוי תאריכי טיסה, כמו היום); × על לילה בקצה מקצר.
- לילות רצופים באותה עיר מתאחדים אוטומטית ל**מקטע** אחד. מתחת לרצועה - רשימת המקטעים, ולכל אחד בחירת מלון. "להוריד מקטע" = להעביר את הלילות שלו לעיר השנייה.
- מגבלה: עד 3 מקטעים (A→B→A). לחיצה שיוצרת רביעי נחסמת עם הסבר קצר.
- ויתור על מלון: הכול או כלום (כמו היום).

### 2.4 מחיר
מחיר בסיס אחד לאירוע (`base_hotel_price`, לאדם) = המלון הזול (3★) בכל מקטע של **מסלול ברירת המחדל**, מסוכם, + המרווח הרגיל פעם אחת. הלקוח שינה חלוקה / בחר מלון אחר → רואה +/- מול הבסיס, אותו מנגנון כמו היום. אין מנגנון מחיר חדש.

### 2.5 כרטיס האירוע באתר (תשובה 6)
עיר האירוע ≠ עיר הטיסה → "ליברפול · טיסה למנצ'סטר". זהות → כמו היום.

### 2.6 שלבים
- **C1 - עיר אחת לכל השהות:** מצבי "בלבד" + כפתורי "הכול ב…" (בלי רצועה). ההזמנה נשארת עם מלון אחד → אין שינוי במבנה ההזמנה, במיילים ובדוחות. + שורת "טיסה ל…" בכרטיס.
- **C2 - רצועת הלילות ושהות מפוצלת:** כמה מלונות בהזמנה אחת → אישור הזמנה, מייל ללקוח, מסך הזמנות ודוחות, הצעות מחיר. אופליין וסוכנים - לא בשלב הזה.

### ❓ פתוח
4. רדיוס חיפוש מלונות לכל Location? (לא נענה)
11. **נעילת ליל האירוע - תמיד, או הגדרה לאירוע?** מנצ'סטר-ליברפול = 50 דק' רכבת; הרבה אוהדים ישנים במנצ'סטר גם בליל המשחק בליברפול. אם הנעילה קשיחה, "הכול במנצ'סטר" בלתי אפשרי למשחק של ליברפול. הצעה: מתג לאירוע "ליל האירוע נעול לעיר האירוע" - דלוק לערים רחוקות (אמסטרדם/המבורג), כבוי לקרובות.
12. **"להוריד מקטע"** - הבנו: להעביר את הלילות לעיר השנייה. או שהכוונה גם ל"לילות בלי מלון בכלל" (ישן אצל חברים)? השני מסבך מחיר (דמי ויתור חלקיים).
13. **תשובה 8** - הבנו: *אופליין* לא צריך לתמוך במפוצל כרגע. לא: "מפוצל לא נדרש כרגע". נכון?
14. **הגדרה בכמות:** "כל משחק במנצ'סטר/ליברפול" = עשרות אירועים. הצעה: מגדירים את הזוג פעם אחת ב-Locations (מנצ'סטר ↔ ליברפול), אירוע חדש באחת הערים מקבל את העיר הנוספת אוטומטית, + פעולת bulk בטבלת האירועים לקיימים.
15. **ברירת מחדל לזוג הזה:** למשחק בליברפול - נפתח על ליברפול או על מנצ'סטר? למשחק במנצ'סטר - ליברפול מוצעת בכלל?

## 3. חלק B - חימום מלונות ליעד (עדיפות אחרונה)

ההבנה אושרה: יעד חדש = אין אצלנו דאטא של מלונות; גלעד טען ידנית בעבר; היום זה מתמלא רק מגלישת לקוחות (עד 14 מלונות לטעינת דף), ועד אז אין מלונות 3★ לחישוב מחיר בסיס.

**מגבלות RateHawk (נמדד 20.09, `/api/b2b/v3/overview/`):** `hotel/info` 30/דקה · `serp/geo` 10/דקה · `serp/hotels` 150/דקה · dumps 100/יום. משותף עם תנועת הלקוחות והקרונים → חימום ב-~12 מלונות/דקה, עוצר על 429. יעד של 150-250 מלונות ≈ 15-20 דקות, פעם אחת.

**מה ייבנה:** כפתור "טען מלונות" ב-Locations ובכרטיס המיקום בעורך (שורת מצב, ניתן לעצירה, ממשיך מאיפה שנעצר) · אוטומטי אחרי יצירת Location · ריצה לילית לאזורים שמעולם לא נטענו · רענון אחרי 90 יום · `city` אמיתי במקום "Missing".

## נספח טכני (לדור)

**מצב קיים:** `events.location` jsonb יחיד (נקודת ה-venue + `city_iata`) מזין גם את `destinationLocationCode` וגם את `/api/hotels` (radius 2000 / 5000 US, hardcoded ב-`fetchHotels.ts` + `portal-package-actions.ts`). `hotels` מתמלאת רק ב-`/api/hotels-info` (`slice(0,14)`, upsert לא ב-await, `city:"Missing"`). GET של base price מסנן `star_rating=3` דרך `hotels`. אין `location_id`, אין `skip_hotel`; `skip_flight` true ב-428/436.

**A:** `events.package_mode text not null default 'package'` (`'ticket_only'`; ללא CHECK). Main: `OrderForm` step routing (דפוס ה-US), `isTicketOnlyOverride` כפוי, `EventCard` + `TicketOnlyBadge` (קיים, לא מיובא), `SearchResults`/`HeroSearch`, `metaCatalog`/`activitiesCatalog`, `confirm-order/utils.ts`. Backoffice: עורך (הוצאת `ticket_only_markup` מתחת ל-`skip_flight`), skip ב-`base-price-sync`/`price-light-ours`/`price-alternatives`, scope `na`, פילטר `events-table`, portal wizard. `Event.package_mode` בשני ה-repos.

**C1:** `events.alt_location jsonb {name, latitude, longitude, country_code}` · `events.lodging_mode text default 'event_city'` (`event_city | alt_city | choice_event | choice_alt | split`) · `events.lodging_note text` · `events.lock_event_night bool default true` (תלוי שאלה 11) · `events.flight_city_name text` (לכרטיס; auto-fill מ-`lib/airport-cities.ts`). Main: `requestKey` ב-`HotelFetch.provider` חייב לכלול location (היום לא - שתי ערים יתנגשו); distance anchor ב-`hotels-info` לפי ה-location שנשלח; `OrderHotel.city` + `lodging: 'event'|'alt'`. Backoffice: כרטיס Location שני; `quoteHotel`/`our-offer-detail` על עיר ברירת המחדל; זיווג ב-`locations.paired_location_id` + bulk (שאלה 14).

**C2:** `events.default_stay jsonb` = רשימת לילות-לעיר של מסלול ברירת המחדל, יחסית ליום האירוע (`[{offset:-2, city:'alt'}, …]`) כדי שישרוד שינוי תאריכים. פונקציה pure משותפת `lodgingSegments(nights[]) → segments[]` (merge רצופים, max 3, lock) - mirror בשני ה-repos + selftest. Main: `NightStrip` (client), `HotelSelection` per segment, `fetchHotels` per segment (**`serp/geo` 10/דקה** - מקטעים נטענים סדרתית, לא במקביל; שינוי חלוקה = debounce). `reservations.hotel_order_info` נשאר המקטע של ליל האירוע לתאימות + `hotel_segments jsonb` חדש. נוגע: `OrderReview`, `confirm-order` (+מייל), quotes, reservations + דוחות, `price-quote` (סכום מקטעי ברירת המחדל, מרווח אחד), `base-price-sync`. אופליין: `holdOfflineInventory` לא משתנה - אופליין מוצע רק כשיש מקטע יחיד.

**B:** `POST /api/hotels-warm` ב-main (secret ב-header) → `serp/geo` אחד → diff מול `hotels` → `hotel/info` סדרתי ~12/דקה, עוצר על 429/תקציב → upsert ב-await → `{found, existing, loaded, remaining}`. `hotel_warm_areas` (backoffice-only). Cron לילי + `guardCronRoute` + `?dry_run=1`, בחלון שלא חופף ל-`base-price-sync`/`price-light-ours`.
