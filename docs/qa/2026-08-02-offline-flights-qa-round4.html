M4a

Setting a connection on the way out

Was: "לא נוח, כשלוחצים על 1 צריך להיפתח המיקום"

What changed

There was a bare Stops number near the top of the form and no stopover inputs anywhere on it — the airport fields existed only in the flights-list drawer, on a different screen. So the number and the connection behind it were set in two different places, and nothing kept them in step.

The number is gone. Each leg now has its own Stops choice inside its own section, and choosing 1 stop is what opens the airport and layover inputs, right there.

  1. /offline-flights → New flight. Fill in the usual fields.
  2. Scroll to Outbound Flight. Set Outbound Stops to 1 stop (connection).
  3. Two fields should appear immediately: Outbound Stopover Airport and Outbound Layover. Enter VIE and 2:30.
  4. Save, then open the flight's detail page.

Expect: the two fields appear the moment you pick 1 stop — no saving, no other screen. The detail page reads Outbound Stops: 1 stop · VIE (2:30) and Inbound Stops: Direct.

M4b

Out and back are independent

Was: "צריך להיות הפרדה בין הלוך לחזור"

What changed

One count covered the whole round trip, so a flight was either direct both ways or connecting both ways — there was no way to say "out direct, back through Vienna". The two legs are now separate all the way down, and the old round-trip count is derived from them rather than typed.

  1. Create a flight with Outbound Stops = Direct and Inbound Stops = 1 stop through ATH.
  2. Save, reopen the edit page.
  3. Now make a second flight that connects both ways, through two different airports — say out via VIE, back via ATH.
  4. Save and reopen that one too.

Expect: both survive exactly as entered. Flight 1 comes back Direct outbound / 1 stop inbound — not both, not neither. Flight 2 keeps two different airports rather than copying one across.

M4c

"1 stop" with no airport is refused

The half-filled state that used to sell as direct

Why this matters

This is the shape of the original bug. A flight that claimed a stop but carried no airport had nothing to show the customer, so it rendered as direct — the flight said one thing and the booking page said another.

  1. On a new flight, set Outbound Stops to 1 stop.
  2. Leave Outbound Stopover Airport empty. Try to save.
  3. Now put a nonsense code in it — XX, or VIENNA.
  4. Fix it to VIE and put 90 minutes in the layover.

Expect: step 2 refuses with "A connecting leg needs its stopover airport" — it must not save quietly as a direct flight. Step 3 refuses too (three letters). Step 4 refuses the layover — it wants 1:30. Each message points at the field it's about.

M4d

Editing a connecting flight keeps its connection

Round 3's trap: editing used to flatten it back to direct

What changed

The edit form used to reload the stop count as a hardcoded 0, so opening a connecting flight and pressing Save turned it direct. It now reads the real stopover off the row, and converts the database's 02:30:00 back into 2:30 so a re-save doesn't fail on its own value.

  1. Open the connecting flight from M4a in the edit page.
  2. Check the layover reads 2:30, not 02:30:00.
  3. Change something unrelated — the price. Save.
  4. Reopen. Then switch Outbound Stops back to Direct, save, reopen again.

Expect: the connection survives step 3 untouched — this is the exact case that used to eat it. After step 4 the airport and layover are cleared, not left behind as orphans on a flight now calling itself direct.

M4e

Setting a stopover from the flights list

The drawer is the fourth way in, and it writes one field at a time

What changed

The drawer saves a single field per edit, so it can't work out the round-trip count on its own — and the old editable Stops column let you set a count here that nothing kept true. That column is gone; the database now derives the count from the airports on every write, whichever screen the write came from.

  1. In /offline-flights, click a row id to open the drawer.
  2. Set In stopover to ATH. Close the drawer.
  3. Open that flight's detail page.
  4. Reopen the drawer and clear In stopover again.

Expect: after step 3 the detail page reads Inbound Stops: 1 stop · ATH with Outbound Stops: Direct — the return leg alone. After step 4 it is back to Direct both ways. There is no editable Stops column in the drawer any more; the stopover airports are what you set.

S1

A whole series of connecting flights

The series builder used to force every row direct

What changed

The builder wrote a hardcoded 0 into every row it made, so a series of connecting flights was impossible — you'd have had to open all twenty afterwards and fix them one at a time.

  1. /offline-flights → New series.
  2. In step 1, fill in the template and set Outbound stopover to VIE with layover 2:00. Leave the return blank.
  3. Note that Outbound layover is greyed out until you type an airport.
  4. Pick three departure dates, build the series, save it.
  5. Open two of the created flights.

Expect: every flight in the series carries the same connection — 1 stop out via VIE, direct back. Not just the first row.

M6

A sold-out locked package says so on the card

Was: "בעמוד של אנדרה ריו הכרטיס צריך להיות סולד אאוט - זה לא קורה"

What was actually wrong

The catalog decided sold-out from ticket availability alone. A locked package sells one offline flight and deliberately has no fallback to a live search — so when that flight empties the package is finished, but its tickets still said "available" and the card kept advertising it. The customer only found out at the flight step.

The card now also fails a locked package whose flight is empty, using the same two limits the flight search uses: the flight's own seat pool, and the event's allocation on it.

  1. On a test event, lock the package to a flight that has free seats.
  2. Find that event's card on the homepage or in search — it should look normal.
  3. Now set the event's allocation on that flight to 0 and save.
  4. Reload the homepage. (The catalog caches for up to an hour — if nothing changes, wait or ask Dor to trigger a revalidate.)
  5. Open that event's order page and walk to the flight step.

Expect: after step 4 the card reads אזלו הכרטיסים and drops out of search. Step 5 shows the "החבילה אזלה" panel — and critically no live flight results in its place, which would silently re-price the package. Card and order page must agree; them disagreeing is the whole bug.

M6b

Unlocked events are untouched

The new rule must not hide anything else

  1. Pick three events that are not locked, with tickets available.
  2. Check they still appear on the homepage and in search.
  3. Check an event you know is genuinely sold out still reads sold out.

Expect: nothing changes for any of them. The new check only ever looks at events with a locked flight; everything else takes the old path exactly as before.

L1

No "other dates?" popup on a locked package

Was: "עושים LOCK ומגיעים לעמוד טיסה שלא יקפוץ הפופ אפ"

What was actually wrong

The tooltip opens itself on a timer after the page loads, and it never checked whether the date picker was usable. On a locked package the dates are the flight's and the picker is disabled — so it was popping up to offer an action it had just taken away.

  1. Open the flight step for a locked event.
  2. Wait a few seconds without touching anything.
  3. Now open the flight step for a normal, unlocked event and wait again.

Expect: nothing pops up in step 2 — the date picker stays quietly dimmed with its "תאריכי החבילה קבועים לפי הטיסה" hover text. In step 3 the "רוצים לטוס בתאריכים אחרים? בחרו כאן" tooltip still appears as it always did. Losing it there would be a regression.
