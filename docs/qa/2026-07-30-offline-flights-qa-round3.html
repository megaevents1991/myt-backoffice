M4

A stopover flight stops calling itself direct

Was: still pinned to 0

"1.still pinned to 0"

What was actually wrong

You were right, and my first fix was incomplete. stops was pinned in four places; adding it to the drawer's field list opened only one of them:

· z.literal(0) in all three flight schemas — Zod rejected any connecting flight outright
· the Stops input was readOnly on both the new and edit pages
· the edit form reset stops to a hardcoded 0, so editing a connecting flight flattened it back to direct on save

That last one was the trap: you could set a stopover in the drawer, then lose it just by opening the edit page and saving. I confirmed the database itself accepts stops = 1 before touching any UI, so the constraint was never the problem.

  1. Open a flight's edit page. Set Stops to 1 and save.
  2. Reopen the edit page — is it still 1?
  3. From the flights list, click the row id to open the drawer. Set Out stopover to e.g. VIE and Out stop duration to PT2H.
  4. Go back to the edit page and save again without changing anything.
  5. Check the flight card on the live site.

Expect: stops sticks at 1 through both saves, the stopover survives step 4, and the card shows one stop rather than direct. Step 4 is the regression that used to eat it.

M5

A locked package offers exactly one flight

Was: the lock didn't save

"when i save lock flight and then go out of event it is not really saved"

What was actually wrong

The lock was written — and then the event's own Save wiped it. lockEventFlight writes locked_flight_id straight to the database, but the page never folded the new value into its own copy of the event. So saving the event wrote back the value loaded when the page opened — null — silently unlocking the package.

The form now withholds locked_flight_id entirely, since the lock actions own that column, and the panel reports the new value back so local state stays honest.

  1. On a test event, lock the package to a flight with free seats.
  2. Save the event, leave the page, come back.
  3. Now lock it, edit something unrelated on the event (the name), and save.
  4. Open the flight step for that event on the live site.

Expect: the lock survives both steps 2 and 3 — step 3 is the exact case that used to break it. On the site: that one flight only, no sort tabs, no filter sidebar, dates fixed, and Amadeus never called.
